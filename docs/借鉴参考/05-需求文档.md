# 需求文档：传播推演决策引擎升级

## 1. 背景

MiroFish-local 当前已经可以完成事件输入、图谱构建、Agent 人设生成、双平台社交仿真、报告生成和深度互动。但它更偏“传播模拟与预测报告”，而不是完整的“传播决策支持系统”。

参考 Decitron 公开资料中的信号感知、决策场景、多路径推演、方案评估和持续追踪能力，本需求文档定义 MiroFish-local 的升级方向：将现有项目升级为“传播推演决策引擎”。

## 2. 产品目标

### 2.1 核心目标

让用户不仅能看到“舆情可能如何传播”，还能比较“不同干预方案会导致什么结果”，并在后续外部信号变化时更新判断。

### 2.2 一句话定位

输入事件与决策目标，系统自动构建传播场景，生成多个干预情景，运行多 Agent 推演，输出量化对比、风险路径和行动建议。

## 3. 目标用户

| 用户 | 核心诉求 |
| --- | --- |
| 危机公关负责人 | 评估不同回应策略的传播风险和时机 |
| 舆情分析师 | 识别传播路径、关键节点和风险信号 |
| 公共治理人员 | 预演政策/事件发布后的公众反应 |
| 媒体/传播研究者 | 分析群体行为、扩散路径和意见演化 |
| 品牌/企业战略团队 | 评估事件对品牌信任和公众态度的影响 |

## 4. 用户故事

### 4.1 危机公关场景

作为危机公关负责人，我希望输入一个突发负面事件后，系统能自动生成“快速回应、延迟回应、第三方背书、平台降权”等多个处置情景，并比较哪个方案更可能降低负面扩散。

验收标准：

- 用户可以选择或创建多个情景。
- 每个情景保留独立配置和运行结果。
- 报告展示关键指标对比和推荐策略。

### 4.2 舆情追踪场景

作为舆情分析师，我希望系统在初次推演后持续追踪外部信号，当出现新的媒体报道、官方回应、反转证据时，系统能提示这些信号会影响哪条路径。

验收标准：

- 用户可以为项目开启信号追踪。
- 系统保存信号来源、时间、摘要、相关变量和影响等级。
- 报告能引用新增信号并提示是否需要再推演。

### 4.3 决策复盘场景

作为研究者，我希望系统能保留每次推演的条件、假设、参数和结果，方便后续与真实事件发展对比，逐步提高模型可信度。

验收标准：

- 每次情景运行有可追溯快照。
- 关键判断有对应证据和假设。
- 后续可记录真实结果并做回测。

## 5. 功能需求

### FR1：决策问题结构化

在 Step1 增加“决策问题结构化”能力。

输入：

- 用户推演方向
- 事件摘要
- 补充上下文
- 来源材料

输出：

```json
{
  "decision_goal": "降低负面舆情二次扩散",
  "time_horizon": "72小时",
  "target_outcomes": ["负面声量下降", "避免二次峰值"],
  "actors": ["官方机构", "媒体", "KOL", "公众"],
  "key_variables": ["官方回应时间", "证据强度", "媒体跟进", "平台推荐"],
  "candidate_interventions": ["2小时内回应", "发布证据链", "邀请第三方说明"],
  "risk_signals": ["媒体持续跟进", "KOL质疑", "新证据反转"]
}
```

验收标准：

- 后端能返回结构化 JSON。
- 前端可展示并允许用户编辑。
- 结构化结果会随项目保存。

### FR2：情景配置与快照

用户可以基于一个项目创建多个情景。

情景字段：

- 情景名称
- 情景描述
- 继承的 baseline simulation config
- 修改过的变量
- 干预动作列表
- 目标指标列表

验收标准：

- 用户能从 baseline 复制情景。
- 情景可保存、查看、编辑。
- 情景运行结果不会覆盖 baseline。

### FR3：干预动作

支持以下干预类型：

| 类型 | 示例 |
| --- | --- |
| 内容干预 | 第 2 轮官方发布回应 |
| 主体干预 | 提高媒体 Agent 活跃度 |
| 平台干预 | 提高病毒传播阈值 |
| 事件干预 | 第 4 轮插入新证据 |
| 立场干预 | 某群体 sentiment_bias 降低 |

验收标准：

- 干预写入情景配置。
- 干预在模拟运行时被应用。
- 报告能说明干预对路径的影响。

### FR4：基础指标评估

基于模拟结果生成指标。

第一版指标：

- total_actions
- post_count
- comment_count
- repost_count
- like_count
- peak_round
- peak_actions
- active_agent_count
- top_agents
- top_quoted_posts
- platform_distribution

第二版指标：

- sentiment_distribution
- stance_distribution
- negative_peak_round
- official_response_delay
- secondary_peak_detected
- rumor_amplification_score

验收标准：

- 每次 simulation 完成后生成指标 JSON。
- 指标可被 Step4 报告和情景对比调用。
- 指标 API 可单独访问。

### FR5：多情景对比报告

对多个情景输出对比报告。

报告结构：

1. 对比摘要
2. 指标对比表
3. 关键路径差异
4. 风险下降/上升点
5. 推荐方案
6. 不确定性与待观察信号

验收标准：

- 用户选择 2 个以上情景后可生成对比报告。
- 报告引用各情景的指标和关键证据。
- 报告能指出推荐方案和理由。

### FR6：外部信号追踪

用户可以为项目开启追踪。

信号字段：

```json
{
  "signal_id": "sig_xxx",
  "project_id": "proj_xxx",
  "source_type": "web_search",
  "source_url": "https://example.com/news",
  "title": "新闻标题",
  "summary": "信号摘要",
  "observed_at": "2026-06-05T12:00:00+08:00",
  "published_at": "2026-06-05T10:00:00+08:00",
  "related_variables": ["官方回应时间"],
  "impact_level": "high",
  "supports_hypothesis": ["二次峰值风险升高"],
  "contradicts_hypothesis": []
}
```

验收标准：

- 可手动刷新信号。
- 信号写入图谱或独立信号存储。
- ReportAgent 可检索信号。
- 信号命中关键变量时提示用户更新推演。

### FR7：概率和置信度雏形

第一阶段先采用经验概率：

- 同一情景多次运行。
- 统计目标事件出现频率。
- 输出经验概率和置信提醒。

验收标准：

- 对比报告能展示经验概率。
- 概率结果明确标注“基于仿真次数，不代表真实统计概率”。

## 6. 非功能需求

### 可追溯性

- 每个情景必须保留配置快照。
- 每个报告必须关联 simulation_id、scenario_id、graph_id。
- 信号必须保留来源 URL 和观测时间。

### 可解释性

- 报告必须给出证据、变量和路径。
- 不能只输出结论。
- 对低置信度结论必须明确提示。

### 隐私与本地化

- 保持 Graphiti + Neo4j 本地模式兼容。
- 不强制依赖外部云图谱。
- 外部搜索可关闭。

### 向后兼容

- 现有五步流程不应被破坏。
- 没有启用情景功能时，原有单次模拟流程继续可用。
- 原有报告生成接口继续保留。

## 7. 成功指标

| 指标 | 目标 |
| --- | --- |
| 情景创建成功率 | 95% 以上 |
| 对比报告生成成功率 | 90% 以上 |
| 指标评估生成耗时 | 单次 simulation 完成后 5 秒内完成基础指标 |
| 用户可编辑字段覆盖率 | 决策目标、变量、干预、指标均可编辑 |
| 报告可追溯性 | 100% 报告关联情景和配置快照 |

## 8. 暂不做

第一阶段暂不做：

- 完整贝叶斯推断引擎
- 大规模历史案例回测
- 非传播领域环境适配器
- 自动执行真实外部干预
- 高频自动化监控和告警
